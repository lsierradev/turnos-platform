[GET] /reservas/health
  Descripcion : Liveness. Solo confirma que el proceso responde; NO toca
                Postgres ni Redis a proposito (si lo hiciera, una caida
                momentanea de la base haria que el orquestador reiniciara
                pods sanos).
  Response 200:
    {
      "status": "ok",
      "module": "reservas"
    }

[GET] /reservas/health/ready
  Descripcion : Readiness (Sprint 9). Ademas comprueba Postgres (SELECT 1) y
                Redis (PING), cada uno con timeout propio de 2s.
  Response 200 / 503:
    {
      "status": "ok" | "degraded",
      "module": "reservas",
      "dependencias": {
        "postgres": { "status": "up" },
        "redis": { "status": "down", "error": "..." }
      }
    }
    Devuelve 503 si alguna dependencia esta caida: el balanceador y el
    orquestador miran el codigo de estado, no el cuerpo.

[POST] /appointments  (requiere Authorization: Bearer <accessToken>)
  Descripcion : Reserva un turno (HU1). El usuario autenticado se toma del
                JWT (sub); `fin` se calcula server-side a partir de la
                duracion del servicio.
  Body        :
    {
      "bahiaId": "uuid",
      "servicioId": "uuid",
      "tecnicoId": "uuid",
      "inicio": "2024-06-10T09:00:00.000Z",
      "clienteId": "uuid"        (opcional, solo admin; Sprint 17)
    }
    tecnicoId debe ser un usuario existente con rol "tecnico".
    clienteId: a nombre de que cliente queda el turno (un admin que reserva
    por un cliente). Sin clienteId, el turno es de quien reserva (sub del
    JWT). Otro rol mandando el id de otra persona -> 403; un id que no es de
    un usuario con rol "cliente" -> 404. El 409 por solapamiento del cliente
    dice "El cliente ya tiene otro turno..." en vez de "Ya tenes otro...".
  Response 201: Turno creado (incluye rangoTiempo { inicio, fin }).
  Response 400 (Sprint 9): inicio en el pasado, o turno que no entra completo
                en el horario laboral 08:00-18:00 hora del taller
                (TZ_NEGOCIO, Sprint 12) (incluido el caso de un
                servicio que empieza dentro y termina fuera). No hay
                antelacion minima: se puede reservar para dentro de 5 min.
  Response 404: bahia, servicio o tecnico inexistente (o el usuario referido
                por tecnicoId no tiene rol "tecnico"). Desde Sprint 17
                tambien una bahia inactiva o un servicio dado de baja.
  Response 409 (double-booking, RF-02 — HU2 bahia, Sprint 4 tecnico):
    {
      "message": "La bahia ya tiene un turno reservado en ese horario.",
      "sugerencias": [
        { "inicio": "...", "fin": "..." },
        { "inicio": "...", "fin": "..." },
        { "inicio": "...", "fin": "..." }
      ]
    }
    El mensaje depende de cual de las TRES constraints EXCLUDE se violo:
      turnos_bahia_rango_excl   -> "La bahia ya tiene un turno reservado..."
      turnos_tecnico_rango_excl -> "El tecnico ya tiene un turno asignado..."
      turnos_usuario_rango_excl -> "Ya tenes otro turno reservado en ese
                                    horario." (Sprint 9, migracion 010)
    Desde la migracion 011 las tres constraints ignoran los turnos
    cancelados: el horario de un turno cancelado se puede volver a reservar,
    y las sugerencias tampoco lo cuentan como ocupado.
    Las sugerencias se buscan sobre el recurso que estaba ocupado: si el
    ocupado es el cliente, sugerir huecos de la bahia devolveria horarios
    que vuelven a dar 409. Las sugerencias son los 3 horarios libres mas cercanos
    para ese mismo recurso (bahia o tecnico) — horario laboral 08:00-18:00,
    ventana de busqueda de 3 dias.

[GET] /appointments/disponibilidad?bahiaId=&servicioId=&tecnicoId=&fecha=YYYY-MM-DD
      (requiere Authorization: Bearer <accessToken>, cualquier rol)
  Descripcion : Horarios reservables de UN dia del taller (Sprint 17): la
                grilla del formulario de reserva. Paso de 15 min dentro de
                08:00-18:00 hora del taller, sin horarios ya empezados, y
                sin pisar turnos no cancelados de la bahia, del tecnico NI
                del propio usuario del token (las tres EXCLUDE).
  Response 200:
    {
      "fecha": "2026-09-25",
      "zonaHoraria": "America/Bogota",
      "duracionMinutos": 30,
      "jornada": { "apertura": "08:00", "cierre": "18:00" },
      "horarios": [ { "inicio": "2026-09-25T13:00:00.000Z", "fin": "..." }, ... ]
    }
  clienteId (opcional, solo admin, mismas reglas que en POST): descuenta
  los turnos de ESE cliente en vez de los de quien consulta.
  Response 400: parametros faltantes, id que no es UUID o fecha inexistente.
  Response 404: mismas reglas que POST /appointments (bahia/servicio
                inactivos, tecnico sin rol).
  Sin cache a proposito: es lo que se mira justo antes de reservar. Puede
  quedar vieja entre la consulta y el POST; para eso esta el 409.

[GET] /appointments/mios  (requiere Authorization: Bearer <accessToken>, cualquier rol)

                bahia, servicio y nombre del tecnico. Sin parametros: no hay
                forma de pedir los de otro.

[GET] /bahias  (requiere Authorization: Bearer <accessToken>, cualquier rol)
  Descripcion : Bahias activas, solo { id, nombre }, ordenadas por nombre
                (Sprint 17, formulario de reserva).

[GET] /technicians  (requiere Authorization: Bearer <accessToken>, cualquier rol)
  Descripcion : Tecnicos, solo { id, nombre } (Sprint 17). Existe porque

[GET] /technicians/:id/agenda  (requiere Authorization: Bearer <accessToken>)
  Descripcion : Turnos del dia para un tecnico (Sprint 4), ordenados por
                hora, con bahia y servicio ya incluidos.
  Query       : ?date=2024-06-10 (opcional; YYYY-MM-DD es un dia del taller,
                TZ_NEGOCIO; default: hoy del taller)
  Response 200: Turno[] (incluye bahia y servicio embebidos)
  Response 404: :id no es un usuario existente con rol "tecnico".

[PATCH] /appointments/:id/estado  (requiere Authorization: Bearer <accessToken>)
  Descripcion : Cierra un turno (RF-04, Sprint 8). Es lo que alimenta los
                KPIs del dashboard: sin esto las columnas estado /
                atencion_inicio / atencion_fin nunca se llenan.
  Body        :
    {
      "estado": "atendido",
      "atencionInicio": "2024-06-10T09:05:00.000Z",
      "atencionFin": "2024-06-10T09:47:00.000Z"
    }
    estado: programado | atendido | no_asistio | cancelado
    atencionInicio/atencionFin son OPCIONALES incluso con estado=atendido
    (no todos los talleres cronometran). Un turno atendido sin esas fechas
    cuenta para la tasa de asistencia y queda fuera del promedio de
    duracion. Si el estado no es "atendido", ambas se limpian.
  Response 200: Turno actualizado.
  Response 400: atencionFin <= atencionInicio.
  Response 404: el turno no existe.
  Response 409 (migracion 011): se intenta sacar de "cancelado" un turno
                cuyo horario ya tomo otro turno (misma bahia, tecnico o
                cliente). Mensaje: "No se puede reactivar el turno: su
                horario ya fue tomado. <recurso ocupado>".

[GET] /dashboard/kpis  (requiere Authorization: Bearer <accessToken>, rol admin o tecnico)
  Descripcion : KPIs operativos del periodo (RF-04, Sprint 8).
  Sprint 18:
    - ?tecnicoId=<uuid> (admin): solo los turnos de ese tecnico. Para el
      rol tecnico se ignora y se usa SIEMPRE su propio id ("Mis
      indicadores"). Un cliente recibe 403.
    - La respuesta suma "zonaHoraria", "tecnicoId" (null = taller entero) y
      "anterior": { rango, resumen } -- el periodo inmediatamente anterior
      de la misma cantidad de dias (hoy -> ayer; 7 dias -> los 7 de antes),
      para comparar cada KPI. Se resuelve en la MISMA consulta.
    - La clave de cache incluye el tecnico.
  Query       : ?from=2024-06-01&to=2024-06-30
                Formato YYYY-MM-DD, ambos inclusive, dias del taller
                (TZ_NEGOCIO, default America/Bogota). Los dos son
                opcionales (default: hoy); si va solo uno, se usa para
                ambos extremos.
  Response 200:
    {
      "rango": { "from": "2024-06-01", "to": "2024-06-30" },
      "resumen": {
        "turnosTotales": 120,
        "turnosAtendidos": 90,
        "turnosNoAsistio": 10,
        "turnosCancelados": 15,
        "turnosProgramados": 5,
        "turnosMedidos": 84,
        "tasaAsistencia": 0.9,
        "minutosPromedioServicio": 42.3
      },
      "serie": [
        {
          "fecha": "2024-06-01",
          "atendidos": 4, "noAsistio": 1,
          "cancelados": 0, "programados": 0,
          "turnosMedidos": 4,
          "tasaAsistencia": 0.8,
          "minutosPromedioServicio": 38.5
        }
      ]
    }
  Response 400: from posterior a to, fecha inexistente, o rango mayor a
                92 dias (tope para acotar el costo de la consulta).

  Definicion de los KPIs:
    tasaAsistencia          = atendidos / (atendidos + no_asistio).
                              Cancelados y programados NO entran en el
                              denominador: cancelar avisando no es una
                              inasistencia, y un turno sin cerrar todavia
                              no aporta informacion.
    minutosPromedioServicio = promedio de (atencion_fin - atencion_inicio)
                              sobre los turnos atendidos QUE TIENEN esas
                              dos fechas. `turnosMedidos` dice sobre
                              cuantas filas se calculo.
    null != 0               : ambos KPIs devuelven null cuando no hay filas
                              para calcularlos ("sin datos"), no 0.
    serie                   : una entrada por dia del rango, incluidos los
                              dias sin ningun turno (en cero).

  Nota de rendimiento (tarea 3 de RF-04):
    La consulta es UNA sola agregacion (no N consultas ni traer filas al
    proceso), filtra por lower(rango_tiempo) para apoyarse en el indice
    idx_turnos_kpi_inicio de la migracion 009, y corre con un
    statement_timeout propio de 5s para no retener una conexion del pool
    que comparte con el motor de reservas. Ver los comentarios en
    dashboard.service.ts y en 009_add_estado_y_atencion_a_turnos.sql.

[GET] /bahias/carga  (requiere Authorization: Bearer <accessToken>, rol admin)
  Descripcion : Carga de trabajo por bahia y por dia (Sprint 16). Alimenta
                el panel administrativo.
  Query       : ?desde=2024-06-10&hasta=2024-06-16
                YYYY-MM-DD, ambos inclusive, dias del taller (TZ_NEGOCIO).
                Opcionales (default: hoy); si va solo uno, se usa para
                ambos extremos. Maximo 31 dias.
  Response 200:
    {
      "desde": "2024-06-10", "hasta": "2024-06-10",
      "zonaHoraria": "America/Bogota",
      "jornada": { "apertura": "08:00", "cierre": "18:00", "minutos": 600 },
      "umbrales": { "alta": 0.8, "completa": 1 },
      "bahias": [
        {
          "bahiaId": "uuid", "nombre": "Bahia 1",
          "dias": [
            { "fecha": "2024-06-10", "turnos": 9, "minutosOcupados": 540,
              "ocupacion": 0.9, "nivel": "alta" }
          ]
        }
      ],
      "resumen": [
        { "fecha": "2024-06-10", "turnos": 14, "minutosOcupados": 780,
          "ocupacion": 0.433, "bahiasEnAlerta": 1 }
      ]
    }
  Response 400: desde posterior a hasta, fecha inexistente, rango > 31 dias.
  Response 401/403: sin token / sin rol admin.

  Definiciones:
    ocupacion  = minutos ocupados DENTRO de la jornada del dia (08:00-18:00
                 hora del taller) / 600. Un turno que empieza antes de la
                 apertura o termina despues del cierre suma solo la parte
                 que cae adentro. Tope 1.
    turnos     = turnos que EMPIEZAN ese dia del taller (un turno a las
                 22:00 locales es de ese dia aunque en UTC sea el siguiente).
    cancelados = no cuentan ni como turno ni como ocupacion. Coincide con
                 las constraints EXCLUDE desde la migracion 011: el horario
                 de un turno cancelado se puede volver a reservar.
    nivel      = "libre" (sin turnos) | "normal" | "alta" (>= umbrales.alta)
                 | "completa" (>= umbrales.completa). Los umbrales viajan en
                 la respuesta para que el front no tenga su propia copia.
    bahias     = solo las activas, incluidas las que no tienen turnos (en 0).
    resumen    = por dia, sobre la capacidad de todas las bahias activas.

  Rendimiento y cache: una sola agregacion (bahias x dias con LEFT JOIN a
  los turnos agrupados), filtro sargable sobre lower(rango_tiempo)
  (idx_turnos_kpi_inicio), statement_timeout de 5 s y cache en Redis con
  clave por zona + rango y TTL de 5 s, igual que /dashboard/kpis. El panel
  refresca cada 15 s: desfase maximo 20 s.

--- Proceso en background (no es un endpoint HTTP) ---

RF-03 — Recordatorio 24h antes del turno (Sprint 6)
  Donde      : reservas-service, NotificationsModule.
  Disparador : cron cada 15 min (NotificationsSchedulerService), busca
               turnos que empiezan dentro de ~24h (banda de +/-15 min).
  Que hace   : inserta una fila en `notificaciones` por canal disponible
               (email siempre; whatsapp solo si el usuario tiene telefono)
               y encola un job de Bull/Redis por cada una.
  Envio      : NotificationsProcessor resuelve el provider segun el canal
               (SendGrid para email, Twilio para WhatsApp) detras de la
               interfaz comun NotificationProvider.
  Reintentos : 3 intentos con backoff exponencial (configurable con
               NOTIFICACIONES_INTENTOS / NOTIFICACIONES_BACKOFF_MS).
  Estado     : tabla `notificaciones` (pendiente | enviado | fallido), con
               `intentos` y `error`. La constraint UNIQUE
               (turno_id, tipo, canal) garantiza que no se mande dos veces
               el mismo recordatorio por el mismo canal.
  Config     : REDIS_URL, ENCRYPTION_KEY, TWILIO_*, SENDGRID_* -- ver
               services/reservas-service/.env.example

  Descripcion : Valida credenciales y emite access + refresh token.

    {

      "password": "password123"
    }

[POST] /auth/olvide  (publico, Sprint 18)
  Body        : { "email": "maria@correo.com" }

[POST] /auth/restablecer  (publico, Sprint 18)
  Body        : { "token": "<43 caracteres del enlace>", "password": "minimo8car" }

  Response 400: enlace inexistente, usado o vencido.
  Los enlaces se guardan como SHA-256 (tabla tokens_contrasena, migracion
  013). Uno nuevo anula los anteriores del mismo usuario. Sin SENDGRID_*
  configurado el correo no sale: queda en el log de usuarios-service.

[POST] /auth/refresh
  Descripcion : Emite un nuevo access token a partir de un refresh token valido.
  Body        :
    {
      "refreshToken": "..."
    }
  Response 200:
    {
      "accessToken": "..."
    }
  Response 401: refresh token invalido o expirado.

[POST] /usuarios  (requiere Authorization: Bearer <accessToken>, rol admin)
  Descripcion : Alta de un usuario. Desde Sprint 17 la usa el formulario de
                reserva para dar de alta un cliente nuevo.
  Body        :
    {
      "email": "maria@correo.com",
      "password": "minimo8car",    (opcional desde Sprint 17, ver abajo)
      "nombre": "Maria Perez",
      "rol": "cliente",            (opcional, default cliente)
      "telefono": "+57 300 ...",   (opcional; se guarda cifrado)
      "ciudad": "Medellin"         (opcional, max 80; migracion 012)
    }
  Sin password (Sprint 18) la cuenta nace con una contrasena al azar que
  nadie conoce y el usuario recibe por correo un enlace para definir la suya
  (vale 72 horas; ver /auth/restablecer). La respuesta suma
  "invitacion": { "enviado": true|false } -- false si SendGrid no esta
  configurado (el enlace queda en el log).
  Response 201: el usuario, sin password_hash.
  Response 400: email invalido, password < 8, nombre vacio, ciudad > 80.
  Response 409: "Ya existe un usuario con el correo <email>." (Sprint 17;
                antes salia el mensaje crudo de Postgres).

[GET] /usuarios?rol=cliente|tecnico|admin  (rol admin)
  Descripcion : Lista usuarios (id, email, nombre, rol, telefono descifrado,
                ciudad).

Pendiente:
  Los refresh tokens emitidos antes de un cambio de contrasena siguen
  validos hasta vencer (7 dias): cambiarla no cierra otras sesiones.

----------------------------------------
Convenciones generales
----------------------------------------
- Sin prefijo global todavia (ej. /api/v1) — pendiente de definir.
- Auth: Bearer JWT (access token de vida corta, 15m por defecto) validado por
  un guard reutilizable (@turnos-platform/auth). El refresh token dura 7 dias
  y solo se valida en /auth/refresh, nunca contra el guard.
- Ambos servicios validan el body con class-validator (ValidationPipe global,
  whitelist activado) — campos no declarados en el DTO se descartan.
- Formato de error estandar (Sprint 9): HttpExceptionFilter global en ambos
  servicios. Todo error responde
    { statusCode, error, message, requestId, timestamp, path }
  El requestId se escribe tambien en el log del 5xx, para poder cruzar un
  reporte del beta con una linea concreta. Los cuerpos ya estructurados se
  preservan: el 409 de double-booking sigue trayendo su array de sugerencias,
  y el ValidationPipe su lista de errores.
  Errores de Postgres que NO son 500: 57014 (statement_timeout) -> 503,
  22P02 (uuid mal formado) -> 400, 23505/23503 -> 409.
- Autorizacion por ROL (Sprint 9): JwtAuthGuard autentica, RolesGuard
  autoriza. Una ruta sin @Roles() sigue abierta a cualquier autenticado.
  Matriz vigente:
    admin                  -> POST/PATCH/DELETE /servicios
    admin | tecnico (suyo) -> GET /dashboard/kpis (Sprint 18)
    admin | tecnico        -> PATCH /appointments/:id/estado
    admin | tecnico duenio -> GET /technicians/:id/agenda (403 si un tecnico
                              pide la agenda de otro)
    admin                  -> GET /bahias/carga, GET /bahias/:id/turnos
    autenticado            -> POST /appointments, GET /servicios,
                              GET /appointments/disponibilidad (Sprint 17),
                              GET /bahias, GET /technicians,
                              GET /appointments/mios (Sprint 18)
    publico                -> POST /auth/login, /auth/olvide, /auth/restablecer
  Falta de permiso responde 403 (el token es valido); 401 queda solo para
  token ausente o invalido.
